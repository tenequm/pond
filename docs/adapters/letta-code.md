# letta-code

Last verified: 2026-08-24, against letta-code v0.30.30 (b2745ce), npm `@letta-ai/letta-code`.

Format archaeology and the decision record for the `letta-code` adapter (issue [#170](https://github.com/tenequm/pond/issues/170)). The adapter code in `packages/pond/src/adapter/letta_code.rs` stays authoritative for extraction behavior; this document records facts about the upstream format and the choices made against them.

## Upstream pointers

- Repository: [letta-ai/letta-code](https://github.com/letta-ai/letta-code). Local clone used for archaeology: `~/pjv/letta-ai/letta-code`.
- Writer: `src/cli/helpers/reflection-transcript.ts` - `TranscriptEntry` union, `lineToTranscriptEntry`, `appendTranscriptDeltaJsonl` (the only append path for interactive, headless and channel producers), `appendExternalTranscriptEntries` (rows imported by `letta dream --from <type>:<path>`), `getReflectionTranscriptPaths`, `sanitizePathSegment`, the reflection payload writers.
- Root resolution: `src/utils/transcript-paths.ts` - `$LETTA_TRANSCRIPT_ROOT`, else `join(homedir(), ".letta", "transcripts")`.
- Producers that call the writer: `src/cli/app/use-conversation-loop.ts:1442` (interactive TUI, on `end_turn`), `src/headless.ts:4869` (`runBidirectionalMode`, on `end_turn` with a success result), `src/websocket/listener/turn-completion.ts:59` (channel listener). The one-shot headless path (`letta -p "..."` without `--input-format stream-json`) never calls it.
- Line ids: `src/cli/helpers/accumulator.ts` - `Line` union; tool lines use the provider tool call id as their line id (`accumulator.ts:1108`); split assistant/reasoning lines take `<id>-split-<n>` ids (`accumulator.ts:877`).
- Legacy state sidecar: `LegacyMessageIdReflectionTranscriptState` (`schema_version: "v2_message_id"`) migrated by `migrateMessageIdState`; current is `v3_assistant_steps`.
- Third-party references consulted, non-authoritative: `@letta-ai/trajectory` (`normalizeTranscript`, the lossy reflection projection - tool arguments capped, no system rows); pond does not read its output.

## Row shapes

Every line of `transcript.jsonl` is one JSON object of one of two shapes (`reflection-transcript.ts:53-70`):

```
{"kind": "user" | "assistant" | "reasoning" | "error", "text": string, "captured_at": string, "source_line_id"?: string, "source_message_id"?: string}
{"kind": "tool_call", "name"?: string, "argsText"?: string, "resultText"?: string, "resultOk"?: boolean, "captured_at": string, "source_line_id"?: string, "source_message_id"?: string}
```

- `captured_at` is `new Date().toISOString()` stamped once per appended turn, so every row of a turn shares it (observed: all rows of a turn carry the same millisecond).
- `source_line_id` is the client line id: `user-<uuid>` (headless) or `user-<base36>-<base36>` (TUI) for user rows, `letta-msg-<n>` for assistant/reasoning rows, the provider tool call id (`toolu_...`) for tool rows. The `letta-msg-<n>` counter is per process, not per conversation: it restarts at 1 in every new process and keeps counting across `/new` conversations in one TUI session (observed: the second conversation of one TUI run starts at `letta-msg-189`). It is therefore not a per-conversation key.
- `source_message_id` is the canonical backend message id when the line learned it; it is set on user/assistant/reasoning rows and never on `tool_call` or `error` rows (`lineToTranscriptEntry`). A reasoning row and its assistant sibling carry different `source_message_id`s in practice (each is the last chunk id of its own stream segment); `state.json` anchors on the assistant one.
- Field history (git, `--follow` across the 2026-05-20 kebab-case rename): the file and the five `kind`s plus `captured_at` date from 9041e600 (2026-03-11, #1348); `source_line_id` from 151a2614 (2026-04-09, #1735); `source_message_id` from a0dd691b (2026-04-21, #1874). Rows written between 2026-03-11 and 2026-04-09 carry neither id.
- Rows from `letta dream --from openhands:<path>` / `--from transcript:<path>` (`appendExternalTranscriptEntries`, 289b2112, 2026-07-07) carry `source_message_id` but never `source_line_id`, land under a synthetic conversation id `from-<type>-<12 hex>`, and are deduplicated on `source_message_id` by the writer.

## Decision table

| # | Decision | Answer | Evidence |
|---|----------|--------|----------|
| 1 | `source_agent` brand | `letta-code`. No kind subpaths: nothing in the transcript tree distinguishes a subagent's conversation from a user's (see row 7). | `getReflectionTranscriptPaths`; the fixture tree. |
| 2 | Session identity | `<agent-dir>/<conversation-dir>`, the two path components under the transcript root, joined with `/`. letta writes both segments through `sanitizePathSegment` (`[^a-zA-Z0-9._-]` becomes `_`, empty becomes `unknown`), and every real id shape already satisfies that alphabet (`agent-local-<uuid>`, `agent-<uuid>`, `default`, `local-conv-<n>`, `conversation-<uuid>`, `from-<type>-<hex>`), so the directory names are the ids and no decoding is needed. The agent prefix is load-bearing: conversation ids repeat across agents (`default` under every agent, `local-conv-1` under every local agent). Decoded once at ingest into `options.source.agent_dir` and `options.source.conversation_dir`. Message ids are `<session>:<line:06>` (the zero-padded physical line number under the session id; a derived tool result adds `:result`): the source line ids are process-scoped counters (row shapes above) and can repeat inside one conversation, so they ride in `options.source.raw_record` instead of keying the row. | `reflection-transcript.ts:605-608, 941-955`; fixture: two agents both holding a `local-conv-1`/`default`. |
| 3 | Project resolution | The agent id (the agent directory name). The transcript carries no cwd anywhere; in letta the shared-state scope of a conversation is the agent (its memory directory is per agent), which is what `Session.project` models. No fallback chain is needed: a transcript always sits under an agent directory. | `getReflectionTranscriptPaths`; fixture rows contain no path field. |
| 4 | Ordering key | `(captured_at, line)`. `captured_at` is one stamp per appended turn, so within a turn only the physical line order carries time; `options.source.line` is the recorded order (restore sorts by it first), and the `<session>:<line:06>` message id is the deterministic tiebreaker. | `appendTranscriptDeltaJsonl:967-976`; fixture turns share one `captured_at`. |
| 5 | Tool-call correlation | One `tool_call` row carries the call and, when it finished, its result. `call_id` = `source_line_id` (the provider tool call id for every TUI/channel row), else `source_message_id` (external rows), else the row's own `<line:06>` position id - the call and result are the same record, so the key is intrinsic to the row, not guessed. Unfinished call = a row without `resultText`/`resultOk`; no result can ever arrive without its call. `is_failure` = `resultOk == false`; an absent `resultOk` reads as not failed (an absence default, not synthesis). `params` = `argsText` parsed as JSON when it parses, else the raw string. Headless one-shot and bidirectional runs drop tool rows entirely (`[REMOVED_ORPHANED_TOOL]` at `end_turn`, observed), so a transcript without tool rows is normal, not broken. | `accumulator.ts:1108`; `lineToTranscriptEntry:707-716`; observed headless log. |
| 6 | Provenance | `user`, `assistant` and `reasoning` text is conversational: the user row holds the typed prompt only - the `<system-reminder>` environment blocks letta prepends live in the backend message store (`lc-local-backend/.../messages.jsonl`), never in the transcript (observed by diffing the two for the same turn). Tool arguments are conversational (model-authored); tool results are injected (runtime-produced). `error` rows and any unknown `kind` are placement rule 3 carriers (system-role message, whole record in `options`). | Fixture rows vs the backend store rows for the same turn. |
| 7 | Lineage | None mapped. Subagents are spawned as separate agents (`--new-agent --tags type:<t>,parent:<agent>`) or as `--agent <id> --new` conversations of an existing agent; the parent link lives only in the agent record's tags in the backend, and no transcript row carries it. Reflection subagents run one-shot headless and write no transcript at all (observed: `/reflect` produced only `payload-auto-*.json`). `parent_session_id` therefore stays unset; inventing it from tags would be synthesis from a source the adapter does not read. | `agent/subagents/manager.ts:234-259`; observed `/reflect`. |
| 8 | Deliberate non-capture | Under `<agent>/<conversation>/`: `state.json` (reflection bookkeeping, `v3_assistant_steps` or legacy `v2_message_id`), `state.json.lock` (transient), `payload-auto-<nonce>.json` (a normalized reflection payload regenerated from the transcript). Under `<agent>/multi-reflection-payloads/`: `payload-{slice,multi,candidates,remember}-<nonce>.json`. All are derived artifacts of the transcript, not the conversation (`model-lossless-projection`). Elsewhere under `~/.letta`: the local backend store (`lc-local-backend/conversations/*/messages.jsonl`, the pi-ai transcript format, plus agent records and memfs git repos), `reflection-arena/`, `logs/` - out of scope for v1; the client transcript exists in every deployment mode and is the only file the reflection pipeline reads. Letta Cloud message history is an API, not a file. | `reflection-transcript.ts:929-935, 1204-1211`; `backend/local/paths.ts`. |
| 9 | Restore face | Native: replay every row's `options.source.raw_record` in message order to `<agent-dir>/<conversation-dir>/transcript.jsonl` - the same path the source occupies, so restoring next to a live install refuses as "already resumed". Foreign, or a native origin whose rows lack `raw_record`: rebuild rows from parts (user/assistant/reasoning text, `tool_call` from a ToolCall part plus its ToolResult sibling, system carriers dropped) and write them to `<agent-dir>/<conversation-dir>-reconstructed/transcript.jsonl` for letta-origin sessions, or `<sanitized project>/<sanitized session id>/transcript.jsonl` for foreign sessions, `sanitizePathSegment`'s own alphabet applied so the directory is one letta lists. | `adapter-native-restore-lossless`, `adapter-restore-distinct-reconstruction`. |
| 10 | Freshness oracle | The last line's `captured_at`. The writer only appends (`appendFile`); nothing truncates or rewrites `transcript.jsonl` (grep of the writer for unlink/truncate/writeFile on the transcript path: none - `ensurePaths` opens it with flag `a`). `state.json` is rewritten but is a sibling file the adapter never reads. A zero-byte file (created by `ensurePaths` before the first turn, or by `/reflect` on an empty conversation - observed) is `Empty` at the seam; an unparsable last line is `Opaque`. No session in the fixture re-reads on an unchanged sync. | `reflection-transcript.ts:722-725, 957-981`. |
| 11 | Windows | `homedir()` resolves to `%USERPROFILE%`, so the root is `%USERPROFILE%\.letta\transcripts`; `LETTA_TRANSCRIPT_ROOT` overrides it on every platform. Paths are built with `path.join`, so separators are native; directory names are already restricted to `[a-zA-Z0-9._-]`. Lines end with `\n` (`appendFile(..., "utf-8")` with the payload joined on `\n`), no BOM, no CRLF. No native Windows capture exists yet; the CI Windows leg runs the same fixture. | `transcript-paths.ts`; `appendTranscriptDeltaJsonl`. |

## Extra format notes

- Producers and what they write. Interactive TUI: every row kind, tool rows with results. Headless bidirectional (`letta -p --input-format stream-json --output-format stream-json`): user/assistant/reasoning/error rows only - tool lines are removed as orphans before the append. Headless one-shot (`letta -p "..."`): nothing. Channel listener (Telegram, Slack, ...): same writer as the TUI. `letta dream --from`: external rows (row shapes above).
- Reasoning rows appear only when the conversation's reasoning effort is set (TUI `/reasoning`, the Tab shortcut after `/reasoning-tab on`, or the agent's `reasoning_effort` model setting) on a model whose catalog entry has `reasoning: true`; the row precedes its assistant sibling within the turn.
- The reflection state machine: `state.json` counts assistant rows (`total_completed_steps`) and records `reflected_through_message_id`, the `source_message_id` of the last assistant row a successful reflection covered. Legacy `v2_message_id` files count turns instead; letta migrates them on read. Neither is ingested.
- Local backend ids differ from cloud ids: local agents are `agent-local-<uuid>`, local conversations `local-conv-<n>` or `default`; cloud agents `agent-<uuid>`, cloud conversations `conversation-<uuid>` (also `conv-...` in older code paths). The adapter treats all of them as opaque directory names.
- Version drift is safe by design: an unknown `kind` still ingests as a rule 3 carrier with the whole record preserved; a `tool_call` row gaining new fields keeps them in `raw_record`.
