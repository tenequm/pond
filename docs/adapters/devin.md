# devin

Last verified: 2026-09-28, against devin 3000.11.3 (commit 9c803229faa4), on macOS and Windows 11.

Format archaeology and the decision record for the `devin` adapter, which reads the local store of Cognition's `devin` CLI (issue [#315](https://github.com/tenequm/pond/issues/315)). The adapter code in `packages/pond/src/adapter/devin.rs` stays authoritative for extraction behavior; this document records facts about the upstream format and the choices made against them.

## Upstream pointers

- Product: the Devin CLI ([docs](https://docs.devin.ai/cli), [stable changelog](https://docs.devin.ai/cli/changelog/stable.md)), installed as the `devin-cli` Homebrew cask on macOS and natively under `%LOCALAPPDATA%\devin\cli` on Windows. The CLI is closed source: there is no writer source to clone and no git history to trace.
- The writer, read from the binary instead: `strings` over `/opt/homebrew/Caskroom/devin-cli/3000.11.3/bin/devin` yields every refinery migration body (`V1__initial_schema` through `V17__subagent_heads`, with their SQL comments) and every statement the session store issues - `INSERT INTO message_nodes (session_id, node_id, parent_node_id, chat_message, created_at, metadata)`, `UPDATE sessions SET main_chain_id = ?1, last_activity_at = ?2 WHERE id = ?3`, `DELETE FROM message_nodes WHERE session_id = ?1 AND node_id BETWEEN ?2 AND ?3` (revert), the per-table `DELETE ... WHERE session_id = ?1` sequence (`devin rm`), `INSERT OR REPLACE INTO tool_call_state`, `INSERT OR REPLACE INTO subagent_heads`, the fork's `INSERT INTO sessions ... SELECT ... FROM sessions WHERE id = ?3`, and the open-time `journal_mode` `WAL` / `synchronous` `NORMAL` / `busy_timeout` pragmas. The binary holds no `UPDATE message_nodes` statement, but it does hold `INSERT OR REPLACE INTO message_nodes`, keyed on `UNIQUE(session_id, node_id)`: a re-save replaces a node row wholesale (row 10). Every shape below that a capture produced was also checked against the sandboxed captures (see Fixture); the rest is marked as binary-only.
- Official docs, cited below as `CL:<line>` of the stable changelog page (as fetched 2026-09-26) plus the commands, subagents and auth reference pages.
- Third-party reference, non-authoritative: the research notes in issue #315 (pointers only; every claim taken from them was re-checked against the binary or a capture).

## The store of record

One SQLite database per install, `<data>/devin/cli/sessions.db`: `$XDG_DATA_HOME/devin/cli/` (default `~/.local/share/devin/cli/`) on macOS and Linux, `%APPDATA%\devin\cli\` on Windows. WAL mode, schema managed by refinery (`refinery_schema_history`, version 17 at 3000.11.3); the CLI runs the pending migrations on every open. Tables:

| Table | Rows | Payload |
|---|---|---|
| `sessions` | one per session, primary key `id` | `working_directory`, `backend_type`, `model`, `agent_mode`, `created_at` / `last_activity_at` (unix seconds), `title`, `main_chain_id`, `shell_last_seen_index`, `cogs_json`, `workspace_dirs`, `hidden`, `metadata` |
| `message_nodes` | one per node of a session's message forest, `row_id` AUTOINCREMENT, `UNIQUE(session_id, node_id)` | `node_id`, `parent_node_id` (NULL for a root), `chat_message` (JSON), `created_at` (unix seconds), `metadata` (JSON `NodeMetadata`) |
| `tool_call_state` | one per tool call, primary key `(session_id, tool_call_id)` | `tool_call_json` (the ACP `ToolCall`) and `tool_call_update_json` (the final `ToolCallUpdate`); the migration comment says resume replays them "instead of reconstructing from the message forest" |
| `subagent_heads` | one per persistent subagent, primary key `(session_id, agent_id)` | `chain_node_id`, `updated_at`; replaced in place on every handoff (`INSERT OR REPLACE`), so it names only the latest head - one row, `sidekick`, in the `sidekick` capture, none elsewhere |
| `prompt_history` | one per typed prompt | `content`, `timestamp`, `session_id`, `is_shell` |
| `rendered_commits` | HTML render cache per session | `sequence_number`, `rendered_html`; empty in every capture |
| `app_state` | global UI key-value | `schema_compat_version` only, in every capture |
| `refinery_schema_history`, `sqlite_sequence` | bookkeeping | |

`message_nodes` holds a forest per session, not a list. Before each model call the harness rebuilds the model context as a new root: the system-prefix messages (node `metadata.is_system_prefix` true) followed by copies of the prior conversation, each copy's node `metadata.extensions."compact/prior_node_ids"` naming the nodes it was copied from. A one-turn `-p` session therefore writes 24-27 nodes for 8-9 distinct messages (`level-waterlily` 27/9, `spotless-lunaria` 24/8), and the whole fixture holds 381 nodes for 172 distinct messages. `sessions.main_chain_id` is the node id of the live head; walking `parent_node_id` from it yields the context exactly as the model last saw it (system prefix included). Everything off that chain - turns before a compaction, the originals of rebuilt copies, the compaction summarizer's own chain, a subagent's chain - stays in the table.

`chat_message.message_id` (a UUID v4) is stable across every copy of a message, but copies are not always byte-identical, and no copy is guaranteed to hold everything the others do. A later copy of an assistant or tool message may add `metadata.extensions."chisel/tool_call_content"` (ACP tool-call content attached after the fact) - measured: 26 of the fixture's 172 messages have more than one variant, and in all 26 every older variant equals the newest with that one key removed. A system-prefix message, though, is rebuilt from the current configuration under the same `message_id`, so a mid-session config change (an `<available_skills>` list, the `You are Devin...` prompt) leaves copies with different `content` where neither contains the other (reported in #315: 12 messages across 11 real sessions, none in the fixture). The newest copy is the one at the highest `node_id`, not `row_id`: node ids are the writer's allocation order and the key `INSERT OR REPLACE` re-saves under, so they survive a re-save, while a re-save renumbers `row_id` (measured: `midrun` kept all 43 node ids, parents and bodies across its re-save and changed all 43 row ids; across all five fixture databases every node's id exceeds its parent's and every rebuilt copy's exceeds each of its `compact/prior_node_ids`, while `amplified-color` has 16 nodes whose `row_id` precedes their parent's). A `/revert` deletes a node-id range, and the reverted `amplified-color` still holds dense node ids 0-124 with every node above its parent afterwards.

`chat_message` keys: `message_id`, `role` (`system` / `user` / `assistant` / `tool`), `content` (always a string), `tool_calls` (`[{id, name, arguments, index, kind: "function"}]`, `arguments` an object), `tool_call_id`, `thinking` (`{thinking, signature}`), `images` (a list of `ImageData`, absent from every captured row; see Images below), `phase` (`final_answer` in the captures, `commentary` too per #315; absent otherwise), and `metadata` (`created_at` as RFC 3339 with microseconds, `is_user_input`, `num_tokens`, `request_id`, `metrics`, `finish_reason`, `started_generation_at`, `generation_model`, `response_dimensions`, `telemetry {source, operation}`, `extensions`). Extensions observed: `subagent/handoff` (`true` on every copy of a sidekick handoff brief, and on nothing else in any capture), `chisel/fusion_lead_model_uid`, `chisel/terminal_output`, `chisel/tool_call_timing`, `chisel/tool_result_meta {success, kind}`, `chisel/tool_call_content`, `chisel/tool_failure {reason: Canceled | ValidationError}`, `chisel/undo`, `chisel/user_question_answers`, `chisel/conversation_history`, `chisel/client-message-id`, `devin-rs/summary {source: file_compactor}`, `affogato/cog-context`, `agent-ext/skills-loaded`, and the subagent link `subagent/{agent_id, chain_node_id, profile_name, model}`. Node `metadata` keys: `summarized_from`, `num_tokens_preceding`, `is_system_prefix`, `extensions {compact/prior_node_ids}`; some nodes carry the JSON literal `null` instead.

## Field history

No git history exists; the embedded refinery migrations are the history. Each version's name and effect:

- V1 `initial_schema`: `sessions(id, working_directory, backend_type, model, permission_mode, created_at, last_activity_at, total_tokens, current_epoch)` and a linear `messages(id, session_id, sequence_number, role, content, tool_call_id, tool_calls_json, timestamp, compaction_epoch)`.
- V2 `add_thinking_column` (`messages.thinking`); V3 `add_prompt_history`; V4 `add_metadata_column` (`messages.metadata`).
- V5 `message_forest`: creates `message_nodes`, drops `sessions.total_tokens` / `current_epoch`, adds `sessions.title` and `main_chain_id`, and ends with `DROP TABLE IF EXISTS messages`. The migration copies no rows from `messages` into `message_nodes`, and no statement in the binary reads `messages`, so the upgrade discards the linear history rather than converting it.
- V6 `add_node_metadata` (`message_nodes.metadata`); V7 `add_shell_context` (`sessions.shell_last_seen_index`); V8 `add_session_cogs` (`sessions.cogs_json`); V9 `add_rendered_commits`; V10 `add_workspace_dirs`; V11 `add_prompt_history_is_shell`; V12 `add_app_state`; V13 `rename_permission_mode_to_agent_mode`; V14 `tool_call_state`; V15 `add_hidden_column`; V16 `add_session_json_metadata` (`sessions.metadata`); V17 `subagent_heads`.

Legacy handling. The CLI migrates on every open, so a database below V5 is one no forest-era CLI has opened, and its `messages` table is its only history. The adapter skips such a database (no `message_nodes`) as `Unsupported`, naming the file, rather than reading it as empty. The reason says the database predates the message forest, which pond does not read, and tells the user to copy the file aside before running a current `devin` on it, because that migration drops the old `messages` table without converting it. No pre-V5 database was available to capture, so the V1 shape is known only from its migration. A version above 17 is read: columns come through `SELECT *`, so a column a later devin adds rides along in the raw record.

## Extra format notes

- Sibling files under `<data>/devin/cli/`: `transcripts/<id>.json`, `summaries/history_<hex>.md`, `logs/`, `session_locks/<id>.lock` (the owning pid), `plugins/`, `app_state.json`, `installation_id`, `skill_events_spool.lock`. `credentials.toml` sits one level up, at `<data>/devin/credentials.toml`, per the auth docs. The legacy root `~/.local/share/cognition/cli` is a compatibility symlink after the CL:1172 migration.
- The ATIF transcript (`transcripts/<id>.json`, ATIF v1.7; the `--export` format) is written by the TUI only - a `-p` headless run writes none - and holds only the live main chain (measured during capture: a TUI session's transcript held 11 steps, with no subagent chain and no reverted branch; `-p` runs wrote no transcript at all). It is a lossy projection of `message_nodes`, hence non-capture.
- devin opens the database with `journal_mode=WAL` and leaves the WAL uncheckpointed, so a live store is a `sessions.db` plus a `-wal` holding the recent rows. The adapter opens read-only through SQLite, which reads the WAL; a copy of the `.db` alone would miss rows. The fixture folds the WAL in and stays in WAL mode.
- `sessions.hidden` (V15) marks sessions that user-facing views skip - per its migration comment the REPL `--list`, `--continue`, prefix resolution and the default ACP agent's `session/list` - and internal helper agents (the summarizer is the example) persist their sessions with it set; the binary's list queries filter `hidden = 0`. pond ingests such a row under `devin/helper` (row 1). No capture produced one (all seven captured rows are 0).
- `sessions.cogs_json` is a JSON array of the harness's context modules ("cogs", 17 per captured session, 25-29 KB): each `{source, lifetime, set_system_prefix, append_system_messages, context, footer_messages, user_display, permissions, tool_availability, model}`. The system messages it appends reach the forest as system-prefix copies; the array itself rides on the Session options. `sessions.metadata` (V16) is the serialized `SessionJsonMetadata`, e.g. `{"total_credit_cost":0,"total_acu_cost":0.0}`; a fork starts without it (the fork `INSERT` does not copy the column) until its next turn writes one.
- Headless `-p` and the TUI write the same tables and the same row shapes; the differences are the missing ATIF transcript under `-p`, the `-p` refusal in an untrusted directory (commands reference), and the Windows first-run Git-provider prompt that blocks `-p`. `--sandbox` makes `autonomous` the only permission mode (essential-commands page).
- Two operations persist nothing (measured during capture): `/btw` runs a side question as a sidechain that is never added to the conversation (commands reference) and wrote no `message_nodes` row and no new session; a TUI started and closed with `/exit` before any message wrote no `sessions` row (CL:453: sessions are saved once the first message is sent).
- `devin rm <session>` (CL:159) is a hard delete: `DELETE FROM` `subagent_heads`, `tool_call_state`, `rendered_commits`, `message_nodes`, `prompt_history` and finally `sessions`, with no trash or soft-delete, refused only while another devin instance holds the session open. `/revert` deletes nodes the same way. Measured during capture: `devin rm` removed the session's rows from `sessions`, `message_nodes`, `prompt_history` and `tool_call_state`. After either, the removed history exists only where something copied it first - which is what this adapter is for.
- Images. `chat_message.images` is a list of `ImageData`, whose shape comes from the binary alone - no capture holds one (the key is absent from all 764 rows across the five fixture databases, so the writer skips an empty list). Its serde field table reads `widthheightbase64_datamime_typesource_pathcaption` next to `struct ImageData with 6 elements`, alongside `ThinkingBlock` (`thinking`, `signature`, `signature_type`) and before `ChatMessageMetadata`; 18 field tables starting `widthheightbase64_data` carry all six fields, 5 omit `source_path` or `caption`, and 5 carry only the first four (some of those are the ACP `ToolContent` image variant, `imagewidthheightbase64_datamime_type`), which suggests `source_path` and `caption` are optional; `base64_data` and `mime_type` are in every table. The binary also holds the paste path (`[Image #`, `failed to persist pasted image`, a `pasted-images` directory) and the `read` tool's image view (`Viewed image`, the system prompt's "read can read images"), the two places an image plausibly enters: typed input and a tool result. Each entry becomes one File part after every other part of its message (user, assistant or tool; a system row keeps its images in the raw record only): `base64_data` verbatim as the inline payload (the whole entry as compact JSON if it lacks one, so the part is never dropped), `mime_type` as the media type and `source_path` verbatim as the file name, each absent when the entry lacks it; `width`, `height` and `caption` have no slot and stay in the raw record. The trailing position is load-bearing: part ids are `<message id>:<ordinal>` and an already-stored id is skipped, so an image placed ahead of the text would take the stored text part's id. A store synced before images were read gains them only when the session is re-read - `pond sync --verify` - since an unchanged session gates fresh.
- The ACP lane (Zed, JetBrains, Xcode, Devin Desktop) appears to share the store: the V15 comment names the default ACP agent's `session/list` as a reader of the same `sessions` table. No ACP-lane session was captured, so this is unverified.
