## The stream of record

Every `updates.jsonl` line is `{"timestamp": <unix seconds, may be 0>, "method": "session/update" | "_x.ai/session/update", "params": {"sessionId", "update": {"sessionUpdate": <kind>, ...}, "_meta": {...}}}` (`storage/mod.rs:584-617`). `method` picks the family: ACP kinds (`user_message_chunk`, `agent_message_chunk`, `agent_thought_chunk`, `tool_call`, `tool_call_update`, `plan`, `current_mode_update`, ...) or x.ai extensions (`turn_completed`, `retry_state`, `hook_execution`, `rewind_marker`, `compaction_checkpoint`, `subagent_spawned`, `subagent_finished`, `image_dropped`, ... 51 variants plus a `#[serde(other)]` sink). A legacy line may be a bare ACP notification with no envelope (`storage/mod.rs:632-643`).

- `params._meta.eventId` is `"{sessionId}-{counter}"` where the counter is a process-global `AtomicU64`, re-seeded on resume with `fetch_max(persisted_max + 1)` (`event_id.rs:24-27, 82-84`): strictly increasing per session, never contiguous, parsed from the *last* `-` segment. Transient (broadcast-only) notifications carry no `eventId` by design, so id-less lines are legal.
- `params._meta.agentTimestampMs` is unix milliseconds; the envelope `timestamp` is seconds and is `#[serde(default)]` - remote-hydrated and imported lines carry a literal `0` (`remote/pull.rs:241-245`), so it is a fallback, never the primary clock.
- The persistence actor merges consecutive metaless agent text/thought chunks into one line before writing (`persistence.rs:1237-1321`), so on-disk `eventId`s are sparse and one line can represent many wire chunks.
- x.ai newtype variants flatten their payload beside `sessionUpdate`; `retry_state` carries its own inner tag as a sibling `"type"` key (`notification.rs:1166-1197`). Enum `rename_all` renames variants only - struct-variant fields stay snake_case (verified on disk: `hook_execution` writes `elapsed_ms`, not `elapsedMs`).
- Tool calls arrive as up to three records sharing `toolCallId`: a `tool_call` (with `rawInput` and `_meta["x.ai/tool"]` = `{version, name, kind, namespace, label, read_only, input?}` - the model-facing tool name lives here, `title` is display text), a statusless enrichment `tool_call_update` (title/kind/locations/content), and a terminal `tool_call_update` with `status: completed | failed` plus `rawOutput` (a `type`-tagged union; a non-zero exit code is still `completed` - `failed` means tool-infrastructure failure, observed on a read of a missing file). An interrupted call is a `tool_call` with no terminal update (observed under SIGTERM).

## Extra format notes

- Canonical mapping (code is authoritative; the shape): each persisted line maps to one canonical unit keyed by its line number. `user_message_chunk` -> User message (text/image content blocks; image blocks carry base64 `data` + `mimeType`); `agent_thought_chunk` -> Assistant message with a ReasoningPart; `agent_message_chunk` -> Assistant message with a TextPart; `tool_call` -> Assistant message with a ToolCallPart (`name` from `_meta["x.ai/tool"].name`, falling back to `title`; `params` = `rawInput`); terminal `tool_call_update` -> Tool message with a ToolResultPart; everything else -> a rule-3 system carrier holding the whole envelope. Every message stores its verbatim envelope line in `options.source.raw_record`.
- `promptIndex` (chunk-level `_meta` on user chunks) is the rewind coordinate, 0-based per turn - and it is *reused* after a rewind (observed: post-rewind resubmission carries `promptIndex: 1` again), so it is not a key; it rides in options.
- The fork copy rewrites `params.sessionId` to the child on every inherited line but preserves `_meta` verbatim, so inherited lines carry `eventId`s prefixed with the *parent's* session id, and the envelope `timestamp` of the whole inherited prefix is the fork second (`copy.rs:202-203`). Neither is used as a key (rows 2, 4).
- The parent records nothing about a fork - no marker in its stream, no summary field (`fork.rs`, `copy.rs` never write source-side). "Children of X" is answerable only by scanning summaries for `parent_session_id == X`; pond's canonical `parent_session_id` makes that a stored fact instead.
- `summary.json` is rewritten on essentially every append (locked read-modify-write, atomic temp+rename, pretty-printed). `updated_at` moves on title-only patches; `last_active_at` is the writer's own activity oracle (`persistence.rs:1053-1057`) - neither is needed by the adapter (the tail peek reads the stream itself), but `last_active_at` is the honest one if a summary-side signal is ever wanted.
- Sessions can relocate wholesale (`$GROK_HOME/relocations/<id>.json` journal; the dir moves between buckets). To ingest, a moved session is just a new path with the same session id - additive sync no-ops the rows already stored.
- Two unrelated products squat `~/.grok`: superagent-ai/grok-cli (npm `grok-dev`) keeps sessions in a `~/.grok/grok.db` SQLite plus `user-settings.json`, and older `@vibe-kit/grok-cli` reads `~/.grok/user-settings.json` too. Neither writes a `sessions/` tree of per-session directories, so discovery keys on `$GROK_HOME/sessions/` containing `<bucket>/<uuid>/updates.jsonl` and never claims the directory for the other products' files.
- Legacy shapes still readable (from back-compat code, single-commit history): un-enveloped bare-notification lines; `chat_history.jsonl` v0 (`ChatRequestMessage` rows, `chat_format_version` absent/0); `summary.json` fields absent on old sessions (every field is `#[serde(default)]`); the `parent_agent_message` alias. Unknown update kinds ingest losslessly as carriers, so post-1.0.6 kinds are covered by construction.
