# opencode

Last verified: 2026-10-12, against opencode v2.0.27 (and v1.19.0 for the V1 store).

Format archaeology and the decision record for the `opencode` adapter's DB-era stores: the V1 `session` / `message` / `part` tables and the OpenCode 2 `session_v2` / `session_message` tables, both inside the same `opencode.db` (issue [#338](https://github.com/tenequm/pond/issues/338): OpenCode 2 writes new sessions only to the V2 tables, so an adapter reading only V1 silently omitted them). The adapter predates the playbook; this is its first spec doc and it covers only the SQLite era. The stale pre-v1.2.0 JSON fan-out tree (`storage/{session,message,part}/...`) is still read, but is described only in the `### opencode` section of `packages/pond/tests/fixtures/README.md`. The adapter code in `packages/pond/src/adapter/opencode.rs` stays authoritative for extraction behavior.

## The V2 rows

- `session_v2` holds typed columns only (no JSON blob): `id`, `project_id`, `workspace_id`, `parent_id`, `fork_session_id`, `fork_boundary` (JSON), `slug`, `directory`, `path`, `title`, `version`, cost/token counters, `agent`, `model` (JSON), `metadata`, `permission`, `revert`, and the `time_*` columns (`time_idle`, `time_viewed`, `idle_outcome`, `time_suspended`, `resume_attempts` are execution state).
- `session_message` is `id`, `session_id`, `type`, `seq`, `time_created`, `time_updated`, `data`. `data` is the encoded `SessionMessage.Info` minus `id` and `type`; the record is `{...data, id, type}` (projector `decodeRow`, [L239-L240](https://github.com/anomalyco/opencode/blob/v2.0.27/packages/core/src/session/projector.ts#L239-L240)). Every record carries `time.created` (millis).
- `seq` is the durable event sequence at INSERT time (`seq: event.durable.seq`, projector L404), unique per session (`session_message_session_seq_idx`) and gapped (events that project no row still consume a number). It is not the order messages began: an assistant row is inserted when its first content is projected, so its `time.created` can predate rows with a lower `seq` (row 4).
- Rows are not immutable. `assistant`, `shell` and `compaction` rows are rewritten in place while they run (streamed content, tool state, `time.completed`, shell output; projector L241-L255), and a committed revert DELETEs every row with `seq >=` the revert boundary (projector L759-L795).
- Ids: `msg_` + 12 hex chars + 14 random base62 chars (`identifier.ts`). The 12 hex chars are the low 48 bits of `ms * 4096 + counter` - the low 36 bits of the millisecond timestamp plus a 12-bit per-process counter - so the 16-char prefix `msg_<12 hex>` names one creation instant (it repeats only every 2^36 ms, about 795 days). Observed: `msg_131ba05dd001...` encodes `1791835637213`, the `time.created` of that row. V1 message ids use the same scheme. Rows projected from an event take the event id with `evt_` replaced by `msg_` (`ID.fromEvent`).

## V1 and V2 in one database

Per `opencode.db` the adapter enumerates V1 `session` ids and `session_v2` ids, each only if its table exists: a fresh OpenCode 2 install may have no V1 tables (the migration itself treats a missing `session` table as "no legacy sessions", [`hasLegacySessions`](https://github.com/anomalyco/opencode/blob/v2.0.27/packages/core/src/database/v1-migration.bun.ts#L1130-L1135)), and a 1.x install has no `session_v2`.

- V1-only session: read exactly as before.
- V2-only session: read from `session_v2` / `session_message`.
- Session in both (migrated by OpenCode 2): the V1 head and the V1 `message` / `part` rows are kept, and only the V2 rows written after the migration are appended. A V2 row is migration-derived - and deliberately not ingested - when its id equals a V1 message id of that session or shares that id's 16-char creation prefix. That covers every row the migration writes: kept ids (`user`, `assistant`, `compaction`), the synthetic split (`syntheticID(userId)`), and the trailing legacy-tool `system` notice (`syntheticID(lastProjectedId)`, whose prefix chains back to a V1 id because the last projected row either kept a V1 id or is itself a split). Post-migration rows are minted later from fresh timestamps, so they never share a V1 prefix (modulo the 795-day wrap of the prefix).
- Session in two DB files: the adapter reads every `opencode*.db`, and the migration imports `opencode-next.db` into `opencode.db` without deleting it, so the same session id can appear twice. `opencode.db` is read first and wins; the repeat is counted as a Superseded skip (`adapter-integrity-dedup`).

This deliberately departs from the issue's suggestion to prefer the V2 content for migrated sessions, for three reasons:

1. `adapter-integrity-additive-sync` requires a newer adapter to produce a superset of a prior version's rows. Earlier pond versions already stored these sessions from V1, under V1 message and part ids; switching them to V2 content would re-key or drop stored rows.
2. The migration is lossy (next section): the V1 rows are the original records and the V2 copies are a projection of them.
3. Migrated rows take `data.time.created` from the V1 `time_created` COLUMN, not from the V1 record's own `data.time.created` ([v1-migration `row()` L878-L897](https://github.com/anomalyco/opencode/blob/v2.0.27/packages/core/src/database/v1-migration.bun.ts#L878-L897) and every `time: { created: item.row.time_created }`). For sessions that passed through opencode's Feb-2026 JSON-tree -> SQLite migration that column is the migration time, so V2 copies of old sessions carry migration stamps where V1 carries the true time.

The `session_v2` head of a migrated session keeps evolving when the session continues (observed: `ses_ece44e9c1ffeJWYCR23BcS31lX` reads `title = "Unknown"` in `session_v2` and `New session - 2026-10-12T20:08:26.942Z` in V1); pond keeps the V1 head it already stored.

## The V1 -> V2 migration

[`v1-migration.bun.ts`](https://github.com/anomalyco/opencode/blob/v2.0.27/packages/core/src/database/v1-migration.bun.ts) runs once per database at OpenCode 2 startup, resumable through the `kv` key `migration.v1-v2` (`{"phase":"completed"}` when done; it never re-runs after that, so rows a 1.x binary writes later stay V1-only). In order:

- Clears the whole `event` table ([L553](https://github.com/anomalyco/opencode/blob/v2.0.27/packages/core/src/database/v1-migration.bun.ts#L553)).
- Imports an earlier V2 database, `opencode-next.db` beside it, if present (the code logs its rows as "previous V2" sessions), copying its V2 sessions and `session_message` rows verbatim ([L702-L837](https://github.com/anomalyco/opencode/blob/v2.0.27/packages/core/src/database/v1-migration.bun.ts#L702-L837)); these become V2-only sessions.
- For each V1 session (newest id first): `INSERT OR IGNORE` into `session_v2` with the same id, deletes any `session_message` rows of that id, then writes `transformSession`'s rows with `seq` 0..n and sets the session's event sequence to the last of them.
- Leaves the V1 `session` / `message` / `part` tables in place - nothing is dropped.

`transformSession` ([L222-L491](https://github.com/anomalyco/opencode/blob/v2.0.27/packages/core/src/database/v1-migration.bun.ts#L222-L491)) is lossy:

- Messages are sorted by the `time_created` column, then id; invalid messages and parts and orphan parts are skipped (logged, not stored).
- A user message: non-ignored, non-synthetic text parts join into `text`; `data:` file parts become base64 `files`; any other file part becomes the text placeholder `[Attachment unavailable after migration: <name> (<mime>)]`; synthetic text parts split off into a second `synthetic` row with id `syntheticID(userId)` = first 16 chars of the user id + a 14-char sha256-derived base62 suffix ([L1067-L1083](https://github.com/anomalyco/opencode/blob/v2.0.27/packages/core/src/database/v1-migration.bun.ts#L1067-L1083)); a message holding only synthetic parts becomes one `synthetic` row under the original id. Subtask-only user messages are dropped, as are assistant messages answering a subtask with a `task` tool.
- A compaction user message and its summary assistant collapse into one `compaction` row under the user id; an errored or incomplete summary drops both.
- An assistant message keeps only `text`, `reasoning` and `tool` parts as `content`. `step-start` / `step-finish` / `snapshot` / `patch` parts survive only as `snapshot.{start,end,files}`; part ids are gone; `time.completed` becomes the row's `time_updated` column; an unfinished V1 tool becomes an `error` state with a synthesized `tool.interrupted` error ([L999](https://github.com/anomalyco/opencode/blob/v2.0.27/packages/core/src/database/v1-migration.bun.ts#L999)).
- Since v2.0.16, when a tool renamed or reshaped in V2 (`bash`, `task`, `apply_patch`, `read` / `edit` / `write`, `skill`, `todowrite`) appears after the last compaction, a trailing `system` row with id `syntheticID(lastProjectedId)` tells the model about it ([L908-L949](https://github.com/anomalyco/opencode/blob/v2.0.27/packages/core/src/database/v1-migration.bun.ts#L908-L949)).
