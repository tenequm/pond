# CI caching architecture: fast, robust, and settled once

Date: 2026-08-24. Owner: tenequm. Status: both rounds landed on the PR branch and measured (results recorded under each round below); round two's cold run 32768577584 and warm-confirm run 32777363790 both passed - the Windows gate is at 9m 6s moon time warm, from 17.8-19.5 min. Remaining: merge #176.

Delivery: both rounds land in ONE pull request from `ci/kache-caching`, one commit per round. A round's first CI run on that PR - forced through the `force_build` dispatch input wherever a number will be read - is the acceptance gate for the next round's commit. Nothing is squashed or reordered: the commit boundaries are what make a single round revertible.

## Goal and constraints

Make the hosted Windows gate (`windows-verify`) fast through caching alone, and make the caching setup something that is configured once and then only bumped on a known trigger, never rediscovered by timing runs.

Fixed constraints, all non-negotiable:

- GitHub-hosted runners stay on the free tier: the standard `windows-2025` image (4 vCPU) for the Windows gate. No larger runners, no paid minutes.
- Heavy compilation (the 3-target dist build, cross-compile) stays on our own ARC runners with the persistent `/ci-cache` PVC.
- What CI checks does not change: the same `cargo clippy --all-targets` and the same full native `cargo test` on Windows, nothing dropped or sampled.
- One job for lint and test on Windows (splitting into two jobs was considered and rejected: it doubles bootstrap and cache fetches for no cache gain).
- Only three jobs are kache consumers: `windows-verify`, `windows-dist` and Linux `build-dist`. Linux `build-and-test` is explicitly out of scope - it never sets `RUSTC_WRAPPER` (only `build-dist` does, root `moon.yml`), the bootstrap merely installs the binary, and its cache is the PVC `target/` directory. Nothing in this document applies to it, and in particular no `kache sync --pull` is ever added to it.

## Where the minutes go (measured 2026-08-24)

Two `windows-verify` runs on PR #173: 19.5 min (`c3ba924`, run 32739660712) and 17.8 min (`138ae45`, docs-only, run 32741714407). Both: ~1 min setup, ~14 min compile, ~3 min running tests (lib 101 s + integration 75 s, versus 9 s + 9 s locally), ~20 s kache post-step. `lint-msvc` runs concurrently and finishes at the same wall time. The kache job summaries decompose the 14 minutes:

- 1450 of 1454 units hit the cache, but every hit paid an on-demand S3 round trip. Average hit overhead 587-881 ms = 289 ms cache-key computation (a `--emit=dep-info` rustc pre-pass plus content-hashing every source file and every `--extern` rlib) + ~300 ms remote demand + 10 ms restore. Aggregate open/setup latency 338-378 s over ~1480 downloads, i.e. ~250 ms per object from a GitHub runner to Hetzner nbg1; read throughput 16 MB/s; 1.1-1.2 GB downloaded per run.
- `Prefetch: 0/1450` in every run. The metric is known-misleading ([kache#618](https://github.com/kunobi-ninja/kache/issues/618), still open: a prefetch that lands on time is consumed as a local hit and scores zero; a maintainer-confirmed 0.12 datapoint shows 1,860 prefetched downloads reported as 0 prefetch hits), so this number alone does not say whether manifest warming ran, and a landed prefetch will always surface as `local:` rather than `prefetch:`. The per-hit remote round trip does say it: hits were served by demand downloads.
- The 287 MB `lance` unit was recompiled (~8 min) in both runs, `lance_namespace_impls` (~2 min) in one. `configuration.mdx` (row `KACHE_REMOTE_RESTORE_TIMEOUT_SECS`): "Synchronous compiler-wrapper demand retains its legacy hard 3s end-to-end ceiling ... Demand expiry reports a miss so rustc recompiles." `lance`'s 57 MB compressed blob at 16 MB/s alone exceeds 3 s. "Failed downloads: 2 / 4" and "Dups: 2 storage duplicates after compile" match: recompiled, then found already stored.
- Uncacheable by design on Windows: the four linked executables (`pond` bin ~1 min, integration harness ~47 s, lib harness ~37 s, ~28 s) because `cache_executables` defaults to false on Windows, the `.pdb` being referenced from outside the binary (this default and the reason for it are taken from `configuration.mdx`, not confirmed in source); the native-lib crates (ring, aws-lc-sys, blake3, zstd, lz4, onig, sqlite3) at most ~9 s each.
- Restore is 10 ms per hit. The NTFS copy is not a cost.

Cold (empty or invalidated cache): 76 min, per the workflow comment.

## Root causes

1. Prefetch does not land before demand. Two paths exist in kache 0.14.2: daemon-startup manifest warming (needs `KACHE_NAMESPACE` and a `Cargo.lock` in the daemon's cwd) and a wrapper hint that fires only on the first local miss after a synchronous `cargo metadata` (~2 min into our build). With 0 prefetch hits and no in-flight joins, neither delivered blobs in the first minutes. The daemon log names the reason and the job never printed it; `kache stats` prints the local/prefetch/remote/dup/miss split, which is the honest measure, and the job never ran it.
2. Per-object latency amplified by the 3 s demand ceiling: the biggest artifacts are exactly the ones that cannot be fetched on demand, so the cache fails on the units that matter most.
3. Version skew: Linux `dist-build` pins kache 0.9.0 (`.github/actions/bootstrap/action.yml`, key schema 21), Windows 0.14.2 (schema 25); v0.15.0 (released 2026-08-24) is schema 27. Two generations coexist in one prefix; the bucket listing at push time shows 23,688 keys. Both schemas sit on the same v3 pack layout (`remote_layout.rs` is already v3 at v0.9.0), so this is one layout with two key schemas, not two layouts.
4. Shared prefix plus a name-only pull filter, and that filter is itself slow. `kache sync --pull` filters by crate name only (`src/cli.rs`, `parse_cargo_lock_crate_names`), so the Linux job's pull (root `moon.yml`, `build-dist`) enumerates every Windows variant too, and enabling it on Windows against the shared prefix would pull most of those 23k keys. Worse, the filtered path is one sequential S3 LIST per lock crate: `list_keys_for_crates` (`src/remote_layout.rs`) loops `for crate_name in crate_names { backend.list(...).await }`, our lock has ~825 crates, and the push-side LIST paced at ~300 ms per request (24 pages over 23,688 keys in 7.2 s), so a lock-filtered pull costs roughly 4 minutes of wall time before a single blob moves. The unfiltered `--all` path is a single paginated LIST of `<prefix>/v3/manifests/` (`list_keys`) and costs seconds. No remote eviction exists ([kache#774](https://github.com/kunobi-ninja/kache/issues/774)).
5. Env-only remote configuration that the next kache breaks: 0.15.0 strips `KACHE_S3_BUCKET/ENDPOINT/REGION/PREFIX/PROFILE/USER_AGENT`, `KACHE_LOCAL_ONLY` and `KACHE_REMOTE_READONLY` from any daemon it spawns itself (`src/daemon.rs`, `AMBIENT_REMOTE_ENV_VARS` / `strip_ambient_remote_env`; [kache-action#23](https://github.com/kunobi-ninja/kache-action/issues/23), confirmed by the maintainers on their own fleet at 0 remote hits). It does not strip the credentials or `KACHE_CONFIG`, which is why "file for the remote, env for the secrets" is the shape that survives. The Linux stub config (`[cache.remote] type = "s3"` with no bucket) is a latent trap rather than an immediate one: 0.15.0 rejects an empty bucket in the file, but while the env bucket is present the CLI still reads env first, so only the env-stripped daemon would ever see the bare stub. The stub is dead weight that misleads and gets deleted, not rewritten.
6. Measurement is not free: moon's remote cache can skip the leg being measured. A CI-only PR (`ci.yml`, `action.yml`, a kache config file) changes none of the declared inputs of `lint-msvc` / `test-msvc` / `build-dist-msvc` (`packages/pond/moon.yml`, root `moon.yml`), so moon serves the hash `main` already stored and cargo never runs - the workflow comment in `ci.yml` says exactly this ("the remote cache is what lets a prose-only commit skip the leg entirely"). A skipped leg produces no kache data, no warm store, no cold run against a fresh prefix, and no useful `workflow_dispatch` prewarm. Every acceptance and prewarm run has to defeat it deliberately.

## Target architecture

- One kache version on both legs, pinned by exact version and action SHA, bumped only on a known trigger (below), never floating.
- Remote settings live in committed per-job config files, `.github/kache/windows-verify.toml`, `.github/kache/windows-dist.toml`, `.github/kache/linux-dist.toml`, each selected by a `KACHE_CONFIG` the bootstrap exports before the kache-action step runs. Not a repo-root `.kache.toml`: a root file is picked up by every contributor who runs kache locally as `RUSTC_WRAPPER` and silently points them at `s3://ttq` with no credentials. Config discovery is identical at 0.9.0 and 0.14.2 (`KACHE_CONFIG` > nearest `.kache.toml` > XDG), so one mechanism covers both legs.
- Each file carries only `[cache.remote]` (type, bucket, endpoint, region, prefix). Everything pond-tunes - `KACHE_CACHE_DIR`, `KACHE_MAX_SIZE`, the prefetch caps, `KACHE_MANIFEST_KEY`, `KACHE_NAMESPACE` (the last two have no file form at all) - stays in env, where the CLI still reads it. `[cache] ignore_env` is never set in these files: it would silence exactly those variables (`src/config.rs`). `FileConfig` is deliberately not `deny_unknown_fields` at 0.9.0, 0.14.2 and 0.15.0, so a newer key added later is ignored by the older leg rather than fatal.
- The file's `prefix` must equal the action's `s3-prefix` input, and the bootstrap asserts it and fails the job if they differ. This is not cosmetic: env beats file for every process at 0.9/0.14, the action always exports `KACHE_S3_PREFIX` and `KACHE_S3_REGION` and gates its daemon and post steps on the `s3-bucket` input, so bucket and prefix cannot leave the action inputs on Windows; and at 0.15 the daemon loses the env prefix while the CLI keeps it, so a mismatch means the daemon prefetches from and uploads to prefix A while `save-manifest` writes prefix B. Prefetch would then silently never land, which is the exact failure this document exists to remove.
- One S3 prefix per build shape, carrying its key-schema tag from the day it is created: `kache/pond/windows-verify/k25`, `kache/pond/windows-dist/k25`, `kache/pond/linux-dist/k21`. Nothing is shared across target triples anyway (`windows-verify` compiles dev deps at opt-level 3 / debug=1, `windows-dist` inherits release plus thin LTO and cgu=1, so the rustc flags differ per unit). Tagging from day one keeps the next rotation a sibling (`.../windows-verify/k27`) rather than a directory nested inside the k25 prefix, which keeps prefix-level bucket GC unambiguous. A prefix is rotated on a key-schema bump; that rotation is the remote GC.
- The store is warmed in bulk before cargo starts with `kache sync --pull --all` run from the bootstrap, not with the action's `sync: true`. `--all` is one paginated LIST plus 16-way concurrent downloads with no 3 s ceiling, instead of 1450 demand fetches or an 825-LIST filtered enumeration. It is only safe because the prefix is per job: `--all` pulls the whole prefix, so the rotation trigger is a size trigger too - rotate when the dry run's `Plan: pull N` exceeds about twice the working set (1450 units / 1.2 GB). Daemon prefetch stays as a second layer.
- Diagnostics are permanent and shaped so they can never be what fails the gate: a fail-fast `kache stats` immediately after the kache-action step (the one kache step allowed to fail the job), and a job-level diagnostics step in both `windows-verify` and `windows-dist` with `if: always()`, `continue-on-error: true`, `timeout-minutes: 2`, `shell: pwsh`. `kache stats` is the measurement source. The daemon log is read as a file, never through `kache daemon log`.
- Every acceptance run and every prewarm run sets `MOON_FORCE=true` through a `workflow_dispatch` input, so moon's remote cache cannot skip the leg being measured. The value has to be the literal `true`: `MOON_FORCE` is the clap env binding for `--force` (`moon run --help`: `[env: MOON_FORCE=]`), not a presence check, so moon parses it as the flag's value and dies with `error: invalid value '1' for '--force'` on anything outside `true`/`false`.
- The Windows job's `CARGO_HOME` is on D: (the fast local disk), not on the slow C: OS disk where the registry sources default to. `RUSTUP_HOME` stays on C:, because rustup's proxies resolve toolchains out of `RUSTUP_HOME` and never read `CARGO_HOME`.

## Ordered slices

Two rounds, not four. The original four slices collapse pairwise because what forces a round boundary is not risk - every kache failure degrades to a plain compile and CI stays green - but measurement: a cold run erases the baseline any other change would be judged against, so two cold-run-causing changes in one commit cannot be attributed. Slice 3 causes no cold run and is read from the same report rows as slice 1, so it joins round one. Slices 2 and 4 both force a cold run, so doing them together pays that run once instead of twice - the same argument the plan already used to fold a `rust-toolchain.toml` bump into slice 4.

What is NOT collapsed, and the reason round one exists at all: the config mechanism must be proven warm once before any prefix is rotated. Rotate and re-configure in one step and a broken config file and a failed rotation are indistinguishable - the run reads as "the rotation did not help" when the truth is "the config never loaded".

Each round is its own commit on `ci/kache-caching`, verified from `kache stats` on that commit's CI run before the next one is written.

Criterion 5 came back far below target - 57.2% and 30.8% by count - and the diagnostics name the cause exactly: hundreds of `restore failed: cached dep-info for <crate> references C:\Users\runneradmin\.cargo\registry\...` evictions ([kache#330](https://github.com/kunobi-ninja/kache/issues/330)) - absolute paths baked into cached dep-info under the OLD default `CARGO_HOME`, unresolvable once `CARGO_HOME` moved to `D:\cargo`, so every such entry was evicted and recompiled, then re-pushed under the new path. A follow-up forced run to prove re-convergence on the old prefix was started, then cancelled - and its salvaged partial log showed the evictions still firing at full volume, which exposed the real mechanism: the cache key does not include `CARGO_HOME`, so a recompiled unit carries the same key as the poisoned blob already in the bucket, and kache never re-uploads an existing blob - the eviction is local, the remote blob is immutable, and the next run re-downloads the same poisoned entry. The old shared prefix can NEVER re-converge for `D:\cargo` runners; rotation is the fix, not merely GC. General rule this hardened: any change that alters absolute paths baked into cached artifacts (a `CARGO_HOME` move, a workspace path change on a self-hosted runner) is a prefix-rotation trigger, exactly like a key-schema bump - land such a change together with a rotation, never alone against a warm prefix. The fresh k27 prefixes are filled entirely from `D:\cargo`-era compiles, so the pathology cannot exist there, and round two's warm-confirm run doubles as the re-convergence proof. Two process rules the measurement taught: never let two runs race one commit (the PR-triggered run and the dispatch ran concurrently, thrashed each other's demand fetches and dup-pushed - cancel the push-triggered twin when dispatching a forced measurement), and read `Compile work avoided` per run, not across racing runs, because concurrent misses double-count.

Still deferred past this round: packed prefetch actually in service: [kache#814](https://github.com/kunobi-ninja/kache/pull/814) is merged but reader-only ("The immutable pack publisher is not implemented yet ... no live S3/R2 publication is authorized by this PR"), so the real trigger is the #812 publisher released and packs being written for our prefix, verified by the `Transport: pack N requests` line #814 added to `kache stats`. Also still deferred: `KACHE_RUNTIME_DIR` per job on the ARC pods once it exists - it is not in v0.15.0 (kache#813 is unreleased; only HEAD documents it), so this waits for the first release containing that PR. Today concurrent pods share `/ci-cache/kache` with one daemon socket and one build-session marker directory. Fold a pending `rust-toolchain.toml` bump into this PR as well (see below). Do all of it in one bump so the cold run is paid once. Acceptance: hit rate unchanged after the cold run, no `no remote configured` lines in the daemon log, `Remote:` in `kache stats` naming the new prefix.

Outside the chain: the `winget-publish` gate ships as its own PR, not inside round one. It is a release-path behavior change and does not belong in a slice advertised as behavior-neutral, and the naive probe is red by construction - `gh` refuses to run inside Actions without `GH_TOKEN`, and `gh api` exits 1 on a 404, which under `set -euo pipefail` fails the step. The shape that works is a `probe` step with `env: { GH_TOKEN: "${{ github.token }}" }` running `if gh api repos/microsoft/winget-pkgs/contents/manifests/t/tenequm/pond >/dev/null 2>&1; then echo present=true >> "$GITHUB_OUTPUT"; else echo "::notice::winget package not yet published (microsoft/winget-pkgs#419055 still open)"; echo present=false >> "$GITHUB_OUTPUT"; fi`, with `if: steps.probe.outputs.present == 'true'` on the winget-releaser step. [microsoft/winget-pkgs#419055](https://github.com/microsoft/winget-pkgs/pull/419055) is still open (refreshed to 0.15.0 on 2026-08-22); once it merges the probe finds the directory and the gate becomes a permanent no-op.

Realistic warm target: about 8 min is the floor with `--all` in place. 1450 hits x (289 ms key computation + 10 ms restore) spread over 4 vCPU is ~1.8 min that no caching change removes, plus 3 min of tests, ~2 min of uncacheable links and ~1 min of setup. Round two lands at 9-11 min; the executable caching folded into round one is what brings it under 10. A lock-filtered pull instead of `--all` would put the same build at ~12 min, which is why `--all` on a per-job prefix is the design and not a preference.

## Execution safety

The cache is a performance layer, never a correctness layer: every kache miss or remote failure degrades to a plain compile, and CI stays green. The things that can actually hurt are wasted cold runs, a red release path, silent slowdowns nobody notices, and measurement runs that measure nothing. Rules:

- Every slice lands as its own commit on the one `ci/kache-caching` PR, so `windows-verify` runs each change on the PR before `main` sees it, and a slice that regresses is reverted by reverting its commit rather than by unpicking a merged branch. Never test a caching change by pushing to `main`.
- Every acceptance run and every prewarm run must be a `workflow_dispatch` with `force_build` set, so `MOON_FORCE=true` bypasses moon's cache. A CI-only diff changes no declared moon task input, so without the force flag moon replays `main`'s stored hash, cargo never runs, and the run yields no kache data, no warm store, and no cold fill of a fresh prefix. No number is read from a run whose kache report shows 0 crates.
- A bad config file makes CI red, not slow, and it is the one caching change with that property. The wrapper calls `Config::load()?` on every compiler invocation, so a TOML typo, a prefix with a backslash or a `.`/`..` segment (rejected by `normalize_remote_prefix`), or an empty bucket at 0.15 kills every rustc call in the job. Hence three guards: the fail-fast `kache stats` step right after the action, which loads the config and prints `Remote: s3://...` and is deliberately allowed to fail the job (it is a config gate, not a connectivity gate - it does not touch the network); the local 0.9.0 rehearsal of the `build-dist` preamble before round one merges, because the Linux leg is release-gated and has no dispatch path to try it on (done: exit 0, 11,198 artifacts planned in 89 s); and the rule that these files carry `[cache.remote]` and nothing else. One correction to the first guard: the exit code is not the gate. A config whose TOML does not parse makes `kache stats` print `Remote: not configured` and exit 0 - measured at 0.9.0 and 0.15.0 - so the step asserts the `Remote:` line names the expected prefix instead of trusting the status.
- Diagnostics are job-level steps, not bootstrap steps: they have to run after `Test`, which a composite action cannot express. Both `windows-verify` and `windows-dist` get them, each with `if: always()`, `continue-on-error: true`, `timeout-minutes: 2`, `shell: pwsh`. `continue-on-error` is load-bearing under pwsh, because GitHub appends an `exit $LASTEXITCODE` check and any non-zero kache exit would otherwise fail the step. Expect an auto-start line in the output: `kache stats` starts a daemon if none is reachable, which is harmless here.
- Never run `kache daemon log` in CI. At v0.14.2 its Windows branch shells out to `powershell -Command "Get-Content -Wait -Tail 50 <file>"`, which follows the file forever and would hold the job to its 180 min timeout; its Linux branch runs `journalctl --user -u kache -f`, and there is no systemd on the ARC pod; and with no log file present it exits non-zero. Read the file instead: the auto-started daemon writes stderr next to its socket, and the socket defaults to `<cache_dir>/daemon.sock`, so on Windows the log is `D:\kache\daemon.log` and the diagnostic is `Get-Content -Tail 200 D:\kache\daemon.log`.
- A cold run must finish. `windows-verify` has `cancel-in-progress: true` on its ref, and the kache post-step (manifest save, final push) runs on `success() || failure()` only, so a cancelled run keeps only what the daemon uploaded in the background and saves no manifest. When a round starts a cold run (a new prefix, a schema bump), push nothing else to that branch until the run completes. Expect ~76 min on Windows. This rule can be relaxed after round two: the daemon uploads blobs during the build (the post step printed "Nothing to sync." after listing 23,688 keys), so once a bulk `sync --pull` is in place a cancelled cold run loses only the manifest and shards, and the next run's pull recovers the blobs.
- Prewarm `windows-dist` before it matters. It runs only on a `main` push that release-plz marks as a release, or on `workflow_dispatch`, and `publish-release` waits for it. After a slice that gives `windows-dist` a fresh prefix or a new key schema, dispatch the workflow once on `main` with `force_build` set and let it finish before the next release PR is merged; without the force flag the dispatch is served from moon's cache and prewarms nothing, and the release then pays the cold build inline.
- A `rust-toolchain.toml` bump is a cold run on both legs, so it is sequenced, not incidental. The pin is 1.95.0 and there is no dependabot or renovate config in the repo, so bumps are manual and can be timed: fold a toolchain bump into a pending schema-bump PR so one cold run covers both, never land one between round two and its measurement, and prewarm `windows-dist` afterwards with the forced dispatch.
- Linux `dist-build` keeps its warm state through prefix changes: `KACHE_CACHE_DIR=/ci-cache/kache` is a persistent local store on the PVC, so hits stay local and only the remote push moves. A cold Linux dist build (~56 min) happens only on a schema bump or a fresh PVC.
- Rollback is a revert, with one caveat. Old prefixes are never deleted, so reverting a prefix change puts the job back on its warm store immediately; reverting a version bump puts it back on the old key schema, which the old prefix still holds. The caveat is that reverting a schema bump does not restore a fully warm store: the old prefix missed every upload made while the new schema was live, and its manifest is stale by that many lock changes, so the first run back is partially warm. Schema tags in the prefix name (`kache/pond/windows-verify/k25` -> `.../k27`) keep the revert a one-line change and keep two schemas out of one prefix.
- `kache sync --pull` failure semantics differ by version: 0.14.2 exits 0 and prints `(N failed)`, so a partial pull is only a slower build; 0.15.0 exits non-zero on any failed transfer. The Linux `moon.yml` pull runs under `set -euo pipefail` and is the place that goes red at 0.15, so round two must pass `--allow-partial` (or put `continue-on-error: true` on the step) so an S3 hiccup cannot fail a job that would otherwise compile through. Inside kache-action the equivalent risk does not exist today: `runKache` uses `ignoreReturnCode: true`, so a failing `sync --pull` there only warns.
- A remote outage is a slow run, not a red one: without the remote every unit compiles locally and the job still passes. Do not add retries or gates that turn cache availability into a job requirement. The pending kache-action#23 fix is expected to violate this by failing when the daemon has no remote; whichever round moves the action SHA past it has to neutralize it. Round one's committed config already removes the underlying regression for us, so the action fix is no longer a precondition for the version bump - only its fail-on-no-remote behavior is, and only if we also move the action pin.
- Correctness risk carried today: kache 0.14.2's key schema 25 can under-key in one shape (swapping two module bodies, or renaming an `include_dir` asset, can preserve the key while changing the compiled program; fixed by schema 26 in 0.15.0, `6cf5649`). If a wrong artifact is ever suspected, `KACHE_KEY_SALT` forces a cold cache without a version change. Round two removes the risk, and it is the main thing round two buys beyond speed.
- Bucket growth is bounded by Cargo.lock churn, not by run count: content-addressed blobs are uploaded once; each dependency change adds its new units (~tens of MB, ~1.2 GB for a full graph). Do not add a bucket lifecycle expiry: kache never re-uploads an existing blob, so expiring old objects would silently turn the warm store cold. The only GC is prefix rotation on a schema bump, plus deleting the previous prefix once its revert window has passed.
- Acceptance is read from `kache stats`, not from wall time and not from the markdown report. `kache stats` is the only output that carries the full `Hit rate: X% (local: a, prefetch: b, remote: c, dup: d, miss: e)` line together with the `Remote:` and `Daemon:` lines that say which prefix and which daemon actually served the run (`src/cli.rs`, `render_stats`). Per round: round one - a forced run with >0 crates compiled, `kache stats` and the daemon log tail visible, dry-run `Plan:` count and elapsed time recorded, hit rate by count >= 99%, the four `pond`/`integration` passthrough rows gone from the report, and no wall-time regression; round two - `remote:` under 5% of hits, "Downloaded (N crates)" under 100 in the post-step report, `lance` absent from "Top compiled cache-key misses", "Cache hit overhead" aggregate well under 5 min, hit rate back to its round-one level once the cold run has filled the new prefix, no `no remote configured` lines in the daemon log, `Remote:` naming the new k27 prefix, under 10 min warm.
- Secrets: fork PRs get no `KACHE_S3_*` secrets and `windows-verify` is already gated to same-repo branches; keep it that way, and keep `KACHE_S3_ACCESS_KEY` / `KACHE_S3_SECRET_KEY` out of any committed file. They are also the two `KACHE_S3_*` variables 0.15's daemon does not strip, which is why credentials belong in env and the remote belongs in the file.

## Deliberately not doing

- Larger runners (paid, and against the free-tier premise).
- Splitting lint and test into two Windows jobs (rejected: no cache gain, double bootstrap).
- A repo-root `.kache.toml`. It would be found by every contributor running kache locally as `RUSTC_WRAPPER` anywhere inside the checkout, pointing them at `s3://ttq` with no credentials, so every lookup pays a request that cannot hit. The config lives under `.github/kache/` and is reached only through the `KACHE_CONFIG` the CI bootstrap exports.
- `[cache] ignore_env` in the committed files: it would silence `KACHE_CACHE_DIR`, `KACHE_MAX_SIZE`, `KACHE_S3_PREFIX` and the prefetch caps, all of which are deliberately env-side.
- The action's `sync: true` / any lock-filtered `kache sync --pull` on Windows: one sequential LIST per lock crate, ~4 min before a byte moves. `--all` against a per-job prefix is one LIST.
- Any `kache sync --pull` in Linux `build-and-test`: it is not a kache consumer at all, and against the shared prefix it would enumerate 23k keys on every PR.
- `kache report --format markdown` as a job step: the action's post step already publishes a report to the job summary, and `kache stats` is the acceptance source, so a second report is noise.
- `kache daemon log` anywhere in CI (it follows the log forever on Windows and needs systemd on Linux).
- Dev Drive / ReFS via `samypr100/setup-dev-drive`: restore is 10 ms per hit, `target/` already sits on the fast D: disk (the main Dev Drive benefit), Defender real-time protection is already off on `windows-2025`, and uv's own committed setup script says a D: drive "has similar or better performance characteristics than a ReFS dev drive"; a nested VHDX carries a measured 5-10% penalty plus 10-30 s setup.
- `KACHE_WINDOWS_HARDLINK`: the docs forbid it for concurrent builds against one target dir, which `moon run pond:lint-msvc pond:test-msvc` is (doc-sourced; the restriction was not confirmed in source).
- `cache-c-cpp`: switches `cl.exe` to `clang-cl` (a build-correctness change), and C/C++ objects are local-only in kache, useless on an ephemeral runner.
- GitHub Actions cache for the store: 10 GB repo cap, branch-scoped, already rejected in the workflow comments.
- Upgrading to kache 0.15.0 now: costs a cold run per leg and disables the S3 remote with the current daemon-start setup (kache-action#23 is open; the maintainers pinned 0.14.2 across their own fleet for this reason).
- `[profile.dev] debug` changes: already `debug = 1`; `incremental = true` is a no-op under kache (it strips `-C incremental`).
- Caching the cargo registry with `actions/cache`: nets about zero on Windows; `CARGO_HOME` on D: is the version that pays.

## Version and upgrade policy

- Pin kache by exact version on both legs and the kache-action by SHA. The action's `version` input floats to latest by default; never rely on that.
- Bump both legs together, never one. A bump that changes `CACHE_KEY_VERSION` (`src/cache_key.rs`; 21 at v0.9.0, 25 at v0.14.2, 27 at v0.15.0) invalidates the whole store: budget one cold run per leg, rotate the prefixes to the new schema tag, and prewarm `windows-dist` with a forced dispatch afterwards.
- A `rust-toolchain.toml` bump is treated the same way and is scheduled into a pending version-bump PR, so one cold run covers both.
- Triggers to revisit: kache-action#23 merged and `v1` moved to the fixed SHA (read the merged code for the new `KACHE_CONFIG` behavior and the fail-on-no-remote check); kache#812 released so packed prefetch actually publishes, #814 alone being reader-only; kache#813 released so `KACHE_RUNTIME_DIR` exists; any kache release note mentioning the cache-key schema.
- Diagnostics stay in the job permanently; they are how a regression is seen.
