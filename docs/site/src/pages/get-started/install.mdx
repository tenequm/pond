# Install

macOS, Linux, and Windows.

::::code-group

```sh [Homebrew (macOS / Linux)]
brew install tenequm/tap/pond
```

```sh [Nix]
nix profile add github:tenequm/pond#pond
```

```powershell [winget (Windows)]
winget install tenequm.pond
```

```powershell [Scoop (Windows)]
scoop bucket add tenequm https://github.com/tenequm/scoop-bucket
scoop install pond
```

```sh [cargo-binstall (prebuilt)]
# Downloads the prebuilt binary. On Windows this is the x86_64-pc-windows-msvc
# zip, statically linked against the VC runtime - nothing else to install.
cargo binstall pond-db
```

```sh [Cargo (build from source)]
# On Windows this needs protoc (winget install Google.Protobuf) and NASM
# (winget install NASM.NASM) on PATH. macOS and Linux vendor protoc themselves.
cargo install pond-db
```

::::

## Windows

winget is the primary channel. pond is published there as a portable zip, so the install puts `pond` on `PATH`, registers an Add/Remove Programs entry, and `winget uninstall tenequm.pond` reverses it - no MSI and no installer to click through. Scoop is the same binary through a different manager; the bucket updates itself from each GitHub release. Both ultimately fetch `pond-x86_64-pc-windows-msvc.zip`, which is attached to every [release](https://github.com/tenequm/pond/releases) and can also be unpacked by hand.

The zip carries completion scripts for PowerShell, bash, zsh, and fish. Register the PowerShell one by dot-sourcing it from your `$PROFILE` (`. <path>\_pond.ps1`), which needs an execution policy of `RemoteSigned` or looser.

Building from source instead needs two tools the prebuilt binary spares you: `protoc`, because `protobuf-src` cannot vendor it on Windows, and NASM, for `aws-lc-sys`. Embeddings run on the CPU backend.

### Defender and where the store lives

A pond store is many small files, and Defender's real-time scanning charges per file touched - excluding the store directory (`%LOCALAPPDATA%\pond` by default) is worth it if sync or search feels slow. Keep the store on an NTFS volume: local stores commit through a hard-link-and-rename dance that NTFS documents and pond has verified there, while ReFS volumes - including Dev Drive - are unverified for that path. Network locations are rejected outright: a UNC path or a mapped network drive fails at the store URL with an error naming the limitation, because the layers underneath silently drop the host component.

### Long paths

The Windows binary ships a manifest declaring long-path awareness, which only takes effect on machines where the `LongPathsEnabled` policy is also set. Nothing in pond's own path handling depends on it - it is insurance for the bundled C libraries and for tools pond spawns. Cloning this repository is the one case that genuinely needs it, and needs it in git rather than in pond: `git config --global core.longpaths true`.

### WSL

Running the Linux binary under WSL works when both the agent session files and the pond store live on the ext4 side. Do not point either across `/mnt/c`: throughput collapses and Windows-side writes are missed.
