# agy

Last verified: 2026-09-10, against agy 1.2.0 (the `agy` CLI) and the Antigravity ACP server build `release blaze-2026.08.18-1` (`agy_acp_server.par`), on Linux.

Format archaeology and the decision record for the `agy` adapter (issue [#201](https://github.com/tenequm/pond/issues/201)). The adapter code in `packages/pond/src/adapter/agy.rs` stays authoritative for extraction behavior; this document records facts about the upstream format and the choices made against them.

## Upstream pointers

- Product: [google-antigravity/antigravity-cli](https://github.com/google-antigravity/antigravity-cli). The CLI is closed source; that repository is a changelog and issue tracker. There is no writer source to clone and no git history to trace.
- The writer's schema, read from the binary instead: the `agy` 1.2.0 executable (a Go binary) embeds the serialized `FileDescriptorProto` of every message it persists. Extracting them yields the full, named schema - `gemini_coder.Step` / `gemini_coder.Trajectory` (`third_party/gemini_coder/proto/trajectory.proto`) and the `exa.cortex_pb.*` step payloads, enums and metadata (`third_party/jetski/cortex_pb/cortex.proto`, `codeium_common_pb/codeium_common.proto`). Every field number the adapter reads, and every enum value in this document, comes from those descriptors; `protoc --descriptor_set_in=... --decode=gemini_coder.Step` decoded every captured row by name.
- The ACP server's writer source, read directly: `agy_acp_server.par` is a zip of a Google-built Python runtime, and its sources ship inside it (`google3/cloud/developer_experience/antigravity_extensions/acp_server/`). `session_store.py` writes the `.meta` sidecar and rewrites `steps.step_payload` on load (`strip_thought_signatures_from_db`); `paths.py` resolves `<GEMINI_HOME>/antigravity-acp/`; `main.py` logs `Gemini home resolved to ... ($GEMINI_HOME is unset)`. The step rows themselves are written by the Go "LocalHarness" the server spawns, which is the same writer the CLI uses (same tables, same `user_version`, same payload schema).
- Third-party references consulted, non-authoritative: [txcript](https://docs.rs/crate/txcript/latest/source/docs/formats/antigravity.md) (field numbers observed at agy 1.0.16, consistent with the 1.2.0 descriptors), [cross_agent_session_resumer](https://docs.rs/cross_agent_session_resumer/latest/src/casr/providers/antigravity.rs.html) (reads the `brain/` mirror only), [Opendray `antigravity_db.go`](https://github.com/Opendray/opendray/blob/main/internal/session/antigravity_db.go), [agentsview #580](https://github.com/kenn-io/agentsview/commit/2e11aa7a687afb61839ffa29b572bdf6362b29f8) (the encrypted pre-SQLite `.pb` era).

## The store of record

One SQLite database per conversation, `<GEMINI_HOME>/<lane>/conversations/<uuid>.db`, WAL mode, `PRAGMA user_version = 1`. Tables:

| Table | Rows | Payload |
|---|---|---|
| `steps` | one per step, primary key `idx` | columns `step_type`, `status`, `has_subtrajectory`, `step_format`, and blobs `metadata`, `error_details`, `permissions`, `task_details`, `render_info`, `step_payload` |
| `trajectory_meta` | one: `trajectory_id`, `cascade_id` (= the conversation id), `trajectory_type`, `source` | plain columns |
| `trajectory_metadata_blob` | one, `id = 'main'` | `exa.cortex_pb.CortexTrajectoryMetadata` |
| `parent_references` | one per fork / rewind reference | `exa.cortex_pb.CortexTrajectoryReference` |
| `battle_mode_infos` | battle mode only (none captured) | `exa.cortex_pb.BattleModeInfo` |
| `gen_metadata` | one per model generation | `CortexStepGeneratorMetadata` (usage, prompt reconstruction) |
| `executor_metadata` | one per executor run | `ExecutorMetadata` (the resolved `CascadeConfig`) |

`steps.step_payload` is a `gemini_coder.Step`: `type` (field 1, `CortexStepType`), `status` (4, `CortexStepStatus`), `metadata` (5, `CortexStepMetadata`: `created_at`, `source`, the `tool_call` a tool step executes, `model_usage`, `execution_id`, `source_trajectory_step_info {trajectory_id, step_index, cascade_id}`, `internal_metadata.status_transitions[]`), `error` (31), and one payload message per kind in a oneof - `user_input` (19), `planner_response` (20), `generic` (140), `system_message` (114), `agency_tool_call` (116), and about 120 more. The side columns `metadata`, `error_details` and `task_details` are byte copies of the payload's fields 5, 31 and 148 (measured: 62 of 62 `metadata` columns, every non-null `error_details` / `task_details`); `render_info` is not. `step_type` and `status` equal the payload's fields 1 and 4 on every captured row.

In agy 1.2.0's CLI lane every model tool call - file views, directory listings, shell commands, subagent spawns - executes as a `GENERIC` step (type 132) whose `result` holds the model-facing text and whose `payload` (`google.protobuf.Any`) wraps the kind-specific `Step` (a `FIND`, a `VIEW_FILE`, ...). The harness the ACP server spawns still writes the older shape for some tools: the kind's own step type at the top level, with its output in its own fields - `RUN_COMMAND` (type 21, payload field 28, whose `combined_output` 21 is a `RunCommandOutput` message holding the text in `full` 1, else `truncated` 2, else `stdout_output` 19 / the older plain `stdout` 4) and `FIND` (type 25, field 34, `raw_output` 11, else `find_error` 8), both observed on a real install and both still carrying `metadata.tool_call`, which is what pairs them with the planner's declared call. The ACP lane's client-side tools (`client_view_file`) execute as `AGENCY_TOOL_CALL` steps (type 103) whose `response_messages[]` carry an `antigravity.localharness.ToolResponse` (field 1 the tool name, field 2 the JSON result text; the message is not among the embedded descriptors, so its two fields are read as observed).

## Decision table

| # | Decision | Answer | Evidence |
|---|----------|--------|----------|
| 1 | `source_agent` brand | `agy`, the binary name, which covers both writers that share the Gemini home (the CLI and `agy_acp_server`) and stays distinct from the Antigravity IDE. Kind subpath `agy/subagent` for a conversation whose `trajectory_metadata_blob` names a `parent_conversation_id` (a spawned subagent). Forks and ACP conversations are user-visible peers and stay on the root brand; which writer produced a conversation is `options.agy.lane` (`cli` / `acp`), not a kind. | Fixture child `11b9a01c` (`nesting_depth: 1`, agent script `research`); ACP conversations `85732767`, `884ff681`. |
| 2 | Session identity | The database file stem, a UUID that agy itself resumes by (`agy --conversation <uuid>`, ACP `session/load`) and that `trajectory_meta.cascade_id` repeats. Alphabet `[0-9a-f-]`: no `/`, no `:`, `validate_path_id` passes (checked at ingest). Message ids: a step is `<trajectory_id>:<idx:06>` - the trajectory from the step's own `source_trajectory_step_info` (falling back to the table's current `trajectory_id`, and to the shape `step:<idx:06>` when a conversation records neither), the index from the `steps.idx` primary key, which every captured step repeats in `source_trajectory_step_info.step_index`. `:<status>` is appended while the step is still in flight (`pending`, `running`, `generating`, `waiting`, `queued`). A carrier for another table's row is `<table>:<primary key>`, or `<table>:row<position:06>` for a future table whose first column does not identify the row. | `/rewind` measured: deleted steps 2-3 and reused indexes 2-3 under a rotated trajectory id; ACP conversations use `trajectory_id == cascade_id`. |
| 3 | Project resolution | First real datum wins: `trajectory_metadata_blob.workspaces[].workspace_folder_absolute_uri`, then `.workspace_uris[]` (both `file://` URIs, percent-decoded once at ingest; `file:///C:/x` becomes `C:/x`; a bare path is taken as one, and a workspace under any other scheme - a remote workspace - is not a path pond can record and falls through to the next source), then the ACP sidecar's `cwd` (absent, or unreadable because the server was killed mid-rewrite, it is skipped like any other missing datum), then `trajectory_metadata_blob.project_id` - agy's own project scope, which a headless `agy -p` without `--add-dir` records while recording no workspace at all. None of the four is a typed error (`model-project-non-empty`). The source used is recorded as `options.agy.project_source`. `conversation_summaries.db` `workspace_uris` and `history.jsonl` `workspace` are not consulted (row 8). | Fixture `109948f1` (no workspace anywhere in the DB, project `default-cli-project`); every ACP database writes an empty `trajectory_metadata_blob`, so the `.meta` `cwd` is the only cwd. |
| 4 | Ordering key | `(metadata.created_at, message id)`. `created_at` is the writer's own stamp at step creation (nanosecond `Timestamp`); steps are created in `idx` order. Carriers for the trajectory tables sit at the conversation anchor (`trajectory_metadata_blob.created_at`, else the earliest step), the permitted absence fallback. A fork copies its parent's steps with their original `created_at`, so inherited history sorts before the fork's own turns. | Every captured step carries `created_at`; fork `3abd71a7`. |
| 5 | Tool-call correlation | The planner step declares each call in `planner_response.tool_calls[]` (`ChatToolCall {id, name, arguments_json}`); the executing step carries the same `ChatToolCall` in `metadata.tool_call`. `call_id` is that id (`call_<n>`), verbatim on both sides. The result is `generic.result.result` (GENERIC), the `ToolResponse` JSON (AGENCY_TOOL_CALL), or the kind step's own output field (`RUN_COMMAND`, `FIND` - see above), falling back on an `ERROR` step to its `CortexErrorDetails` text; a kind step pond has no output field for stays a rule 3 carrier, with its whole row in the raw record; `is_failure` is `status == ERROR` - a non-zero exit is `DONE` with the exit code in the result text. An unfinished call is a declared call whose executing step is still in flight (a carrier, row 10). A `CANCELED` step keeps whatever the writer left on it - in the fixture, agy's own `Step is still running` note - and maps as a tool result with `is_failure` false; one that carries nothing is a carrier, and no result is ever synthesized for it. A result without a declared call does not occur in the writer. | Tools fixture `3f72cf51` (4 calls: `ls`, a missing-file view in `ERROR`, `false` exiting 1 in `DONE`, a `README.md` view); `121e0cfc` (`RUNNING`), `5d458282` (`CANCELED`, whose result is agy's own `Step is still running` note). The top-level `RUN_COMMAND` / `FIND` shape is not in the fixture - it appeared on a real ACP install (17 commands and one search, each with its `call_id` and its output) and is unit-tested against hand-built payloads. |
| 6 | Provenance | User input text and file parts are conversational: the database holds the prompt exactly as typed - the `<USER_REQUEST>` / `<ADDITIONAL_METADATA>` / `<USER_SETTINGS_CHANGE>` wrapping exists only in the `brain/` mirror, so there is no fused span to split. Planner thinking (reasoning), response text and tool calls are conversational. Tool results are injected. `SYSTEM_MESSAGE`, `EPHEMERAL_MESSAGE`, `CONVERSATION_HISTORY` and `ERROR_MESSAGE` steps are system messages with their text as content (harness-authored: the restart notice, a subagent's report addressed to the model); every other kind is a rule 3 carrier. | Fixture USER_INPUT rows vs their `brain/.../transcript.jsonl` lines; `bb24ae0d` / `5d458282` restart notices; `6479151c` subagent report. Only SYSTEM_MESSAGE was captured of the four, so the other three text fields come from the binary's descriptors rather than a fixture row: `CortexStepSystemMessage.message` 1, `CortexStepEphemeralMessage.content` 1, `CortexStepConversationHistory.content` 1, `CortexStepErrorMessage.error` 3. |
| 7 | Lineage | Both link shapes are child-side, so no cross-tree map is needed. Subagent: the child's own `trajectory_metadata_blob.parent_conversation_id` -> `parent_session_id` (a spawn, no cut point). The parent-side record (`brain/<parent>/.system_generated/subagents/<child>.json`) is non-capture and not needed. Fork: the child's `parent_references` holds `FORK` (2) or `SUBAGENT_FORK` (6) rows; the newest one naming another conversation is the fork -> `parent_session_id` = its `conversation_id`, `parent_message_id` = `<trajectory_id>:<step_index:06>`, which is exactly the parent's message id for the cut step, because the fork copies the parent's steps verbatim (their trajectory ids included). | 9 | Restore face | `restore_unsupported`. agy keeps a conversation as protobuf rows in a SQLite database it mutates in place, and pond deliberately stores the superset of every row version it has seen (row 10) - a rewound branch next to the one that replaced it, an in-flight step next to its settled form - so there is no single native file to write back, and a rebuilt database would also lack the non-captured generator tables agy's loader reads. The reason names the alternative: `pond resume <id> --to claude-code` (or any other target). | The mutation measurements below. |
| 10 | Freshness oracle | The writer is not append-only, measured by snapshotting each database around every mutating operation: a resume rewrote an interrupted step from `RUNNING` to `CANCELED` in place (`status` and `step_payload`); `/rewind` deleted steps and their generator rows, rewrote the rest of `gen_metadata`, rotated `trajectory_meta` and added a `parent_references` row; the ACP server's load path rewrites `step_payload` to strip thought signatures (in source; no captured step carried one to strip); `/fork` wrote a new database and left the parent untouched. The adapter is built for that: step identity is `(trajectory_id, idx)` so a rewind never collides with its replacement, and an in-flight step is keyed by its status so its settled row lands as a new message rather than being latched half-done (the superset posture hermes takes; additive sync never rewrites a stored row). The watermark is the newest step's `metadata.created_at`, read from one row (`ORDER BY rowid DESC LIMIT 1`, the small `metadata` column, falling back to the same message inside `step_payload`) because steps are only ever appended - equal to the newest stored message's timestamp, so an unchanged database gates `Fresh`; a conversation whose newest row records no readable stamp falls back to the largest stamp any step carries, rather than re-reading in full every sync; a database with no `steps` table or no steps is `Empty`; an unreadable one is `Opaque`. Residual: a step that settles in place without a new step being appended does not move the watermark, so the settled form lands on the next sync that sees an appended step (a resume always appends one) or on `pond sync --verify`. Every fixture conversation skips fresh on an unchanged re-sync. | Snapshots taken during capture; conformance `a_second_sync_skips_every_unchanged_session`. |
| 11 | Windows | agy ships a native Windows build; its data root is `%USERPROFILE%\.gemini\antigravity-cli` (per the issue's research, unverified here), the ACP server's is `<GEMINI_HOME>\antigravity-acp`. The format is the same SQLite file, so no encoding quirk reaches the adapter; the one platform-shaped value is the workspace URI, `file:///C:/...`, which decodes to `C:/...` (unit-tested). Discovery joins path components only. Not captured natively on Windows: CI's `windows-verify` runs the whole suite over the Linux fixture, and a native capture (a real Windows cwd surviving as `Session.project`) is the open item. | `file_uris_decode_once`; `probe_default` test. |

## Field history

No history can be traced: the CLI is closed source and its public repository holds no writer code. What the binaries still accept stands in for it:

- `PRAGMA user_version = 1` is the only schema version agy 1.0.9 through 1.2.0 writes (1.0.9 per [antigravity-cli #423](https://github.com/google-antigravity/antigravity-cli/issues/423); 1.2.0 captured). A higher version is skipped as `Unsupported` with an upgrade hint.
- Before the SQLite store, agy kept each conversation as an encrypted `conversations/<uuid>.pb` (read by agentsview through an `agy-reader` sidecar). A `.pb` with no `.db` beside it is skipped as `Unsupported`, never silently; a `.pb` next to its `.db` is the fork copy (row 8).
- The `Step` oneof still carries every kind txcript observed as a top-level step at 1.0.16 (`RUN_COMMAND` type 21 in field 28, `FIND` 25 in field 34, `VIEW_FILE` in field 14, `GREP_SEARCH` in field 13, ...). The CLI lane at 1.2.0 wraps them inside `GENERIC` results; the ACP server's harness still writes `RUN_COMMAND` and `FIND` at the top level, so both shapes are live rather than one being historical. The remaining two kinds txcript saw at top level have not been observed on any writer path at 1.2.0 - the ACP harness executes `view_file` as an `AGENCY_TOOL_CALL` (35 of 36 calls; the CLI lane wraps it in `GENERIC`), and no captured conversation calls a grep tool at all - so they stay carriers; their shapes are recorded here for the day a sample appears: `VIEW_FILE` (type 8, payload field 14, `CortexStepViewFile.content` 4 holds the file body, `raw_content` 9 was never populated in 8 `GENERIC`-wrapped samples; the line-numbered text the model sees is a harness rendering not stored in the step) and `GREP_SEARCH` (type 7, field 13, `CortexStepGrepSearch.raw_output` 3, else `grep_error` 5; `results` 4 is a repeated `GrepSearchResult` message, not a string). A top-level kind step with a `metadata.tool_call` maps to a tool message when pond knows the kind's output field (row 5) or the step errored, and is a carrier otherwise; its whole row survives in the raw record either way.
- `CortexStepUserInput` keeps the deprecated `query` (field 1) beside `user_response` (2) and `items[]` (3); the adapter falls back through all three. `ChatToolCall.thought_signature` (field 6) is the deprecated form of `thinking_signature` (7), per the ACP server's own comments.

## Extra format notes

- Two writers, one home. `~/.gemini/antigravity-cli/` is written by `agy` (TUI and `-p` headless, the same writer - headless persists the same tables, only without a workspace unless `--add-dir` is passed). `~/.gemini/antigravity-acp/` is written by the ACP server, whose credential (`acp_token.json`) and settings are separate from the CLI's. Both lanes share `<GEMINI_HOME>/antigravity-cli/skills/`. `$GEMINI_HOME` relocates the whole tree; a relocated root is configured as an explicit `path` (discovery reads only `~/.gemini`). The public Gemini CLI also lives in `~/.gemini` (`tmp/<slug>/chats/`), so discovery claims the directory only when an agy `conversations/` directory exists under it.
- agy leaves its WAL uncheckpointed on exit: a live database is usually a small `.db` plus a `-wal` holding the recent steps. The adapter opens read-only through SQLite, which reads the WAL, so a copy of the `.db` alone would miss rows; the fixture folds each WAL in with `PRAGMA wal_checkpoint(TRUNCATE)` and stays in WAL mode.
- A resumed conversation gets a `SYSTEM_MESSAGE` step telling the model its subagents and background tasks were stopped by the restart; a subagent's report reaches its parent as a `SYSTEM_MESSAGE` whose `agent_message.sender` is the child's conversation id.
- `metadata.model_usage.model` and `generator_model` are the `exa.codeium_common_pb.Model` enum (`MODEL_PLACEHOLDER_M318` for Gemini 3.8 Flash), not a name; the name agy shows lives in the non-captured `gen_metadata` (`response_model: "gemini-3.8-flash"`) and, on the ACP lane, in `metadata.model_info.model_name`. `options.agy.usage` carries the counters, the raw record the rest.
- The `render_info` column, `permissions`, `task_details`, `requested_interaction`, `user_annotations` and `subtrajectory` (a nested `Trajectory`, flagged by `has_subtrajectory`) are not mapped to parts; they ride in the raw record.
